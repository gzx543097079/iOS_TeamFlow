# 按需求架构生成与审查

适用于生成业务代码、功能扩展及明确的架构重构。需求文档已确认的架构、模块边界和依赖方案是实施约束，不能用个人偏好或模板默认建议替换。已有需求记录和本次用户明确更正可作为依据；无冲突不再次索要确认。

## 实施前判断是否需要映射

先定位需求或工程现状中的既有架构决定。普通功能沿用现有职责和接口，无需逐需求重写映射。只有新增或改变模块边界、依赖方向、状态所有权时，在原需求卡或工程现状补充受影响的职责、位置和接口；其他记录链接引用。

资料缺失时先从相关代码核实。常规实现选择由实际工程和本次目标决定；只有无法安全推断的关键架构取舍或决定冲突才询问，独立工作继续。

- MVC、MVVM、TCA、Clean 等按确认的模式实施，不统一强制 MVVM。明确采用 MVVM 时，View/Controller 负责渲染、布局和输入转发，ViewModel 处理展示状态、业务意图和结果转换，Model/服务负责数据与业务规则；ViewModel 不持有视图或导航控制器。
- 功能模块通过明确接口协作，依赖在上层组装；避免跨功能访问内部状态、服务定位器及循环依赖。外部服务优先构造注入，展示状态来源唯一，核对事件后的界面更新和订阅生命周期；只有这些约定变化时补充记录。
- 先复用现有合适实现；实际共用的样式、组件、数据类型或服务协议放到中立层，不让 Shared 反向依赖具体功能。组件通过数据和回调接入，不读取某页面私有状态。
- 复用需有实际使用方；不为单个场景制造空协议、万能基类或无用途的 Repository/UseCase。目录只是组织方式；需要编译期隔离或独立分发时才拆 Target/Package，并验证真正的依赖边界。
- 若实现必须偏离已确认架构，先说明具体原因、影响和替代方案并取得相应决定，再实施依赖该决定的部分，不能事后用目录或类名宣称符合。

## 生成后核对

按实际改动核对以下适用项，证据在需求卡引用。提交时复用未变结论，仅复查新增差异，不再机械重复完整清单：

1. 需求架构 → 实际类型/职责/依赖一致；不以存在 ViewModel 文件或多建文件夹判通过。
2. 控制器不残留本应属于 ViewModel/服务的筛选、持久化、业务判断；状态更新路径和生命周期明确。
3. 共用组件至少有实际调用方，接口不绑定具体页面；无重复业务规则、依赖反转或循环。
4. 对核心状态与输入输出做独立单元验证，并对迁移涉及的原 UI 主路径回归；编译通过不能证明架构符合，缺失证据如实保持未验证。

可复用未变化的有效证据；本次范围之外的既有架构问题记录边界，不无条件重构全项目。模板目录仅为候选，实际结构以确认的架构映射为准。

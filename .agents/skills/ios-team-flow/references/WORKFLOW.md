# 中文 iOS 团队工作流

版本见 `<SKILL_ROOT>/references/VERSION`。按改动类型加载规范；仅 UI 改动读取 [UI 规范](standards/ui.md)。Codex 原生约定仅指根目录 AGENTS.md 与 `.agents/skills/<name>/SKILL.md` 的发现机制；本文流程是团队约定，不宣称存在官方统一 iOS 工作流认证。

## 1. 接收与需求追踪

先查看 git status、现有工程/文档/构建命令和相关需求，不覆盖已有工作。全新目录尚无 Git 时，在首次需求收尾前于项目根执行 git init；已有仓库使用原根目录，不嵌套。口头需求足以触发追踪：执行 `python3 .agents/skills/ios-team-flow/scripts/delivery.py create --title "需求标题"`，从模板生成 `requirements/REQ-YYYYMMDD-UUID.md`；UUID 在各分支独立生成，不按本地最大序号递增。旧数字编号保持有效。后续同一需求更新原记录，不能每轮对话建一张。

用户只问解释且不要求改动时无需建卡。用户明确取消要记录取消与原因；暂停记录暂停与恢复条件。持续推进已授权工作，只有新项目需求确认、关键缺失业务信息或实际需要授权的外部动作才等待；可独立完成的内容继续做。

## 2. 拆分判断（由 Codex 决定并记录理由）

小需求：单一可验收结果、影响集中、依赖已知、没有迁移或高风险交易/权限状态变更。在一张需求卡中直接执行，保留过程和验证即可。文件数/代码行数不是单独决定因素。

任一情形建议拆分：多个独立用户结果；跨 UI、服务、存储等边界且可分别验证；订阅权益、数据迁移、认证或复杂并发；未知技术方案需要先验证；存在外部依赖/多人协同；难以在一次清晰审查中解释完整变更。

拆分顺序：识别用户结果 → 标依赖和风险 → 按可演示的纵向能力切片 → 高风险先做最小验证 → 每步给验收条件与回退。通常 2–7 步只是参考，不凑步骤、不按文件机械拆分。父卡列子步骤；只有步骤可独立交付或有独立负责人时才另建子卡并双向链接。范围变化可重新拆分，保留原因与原历史。

示例：“改按钮文字”为小卡；“新增订阅中心”为产品配置与模型校验、套餐展示、购买恢复与权益、埋点和端到端验证等依赖步骤。改一行价格也可能涉及交易风险，需要专项核查，但不一定拆成多个卡片。

## 3. 项目类型与需求入口

先区分新产品和已有工程；没有 PRD 或 .xcodeproj 不等于新项目，工程可能由工具生成。已有项目执行 [已有项目流程](EXISTING-PROJECT.md)：首次整理项目现状，之后复用并核对相关变化；只为本次增量创建需求卡，不强制补整份新项目 PRD。多 App/Target 先确定本次目标。工作流/工具仓库维护不属于新建 iOS 产品。

**新项目默认值仅用于新产品草案。已有项目沿用实际语言、框架、部署目标、架构、目录、导航/Tab Bar、主题和其他配置；调整需纳入明确需求范围。**

### 3.1 新项目需求确认（仅新产品加载模板）

按 [新项目模板](templates/new-project.md) 整理已提供材料为 `requirements/PRD-项目名-v1.md`，未知项待确认，不捏造业务规则。默认 Swift + UIKit、最低 iOS 14.0 仅作为待确认建议；按模板的三个阶段确认。创建工程只需批准启动范围及关键配置，功能文案/权限细节在对应功能实施前确认，商店与正式语言范围在发布前确认；不默认勾选 16 种语言。

呈现具体版本供团队确认，记录确认人、含时区时间、原文和版本；没有回复不视为批准。确认后再创建工程与业务代码，验证配置、资源/权限和实际构建运行。重大范围变化只重新确认变化部分。确认前继续整理资料和技术建议。

## 4. 实施与状态机

新需求使用带 `teamflow:requirement:v3` 标记的精简模板；历史卡不批量迁移或补同步。状态只在卡顶部维护一处，验收结果只在 AC 表维护一份，交付索引由脚本生成。不得再填写独立 development 状态、Git 状态、手写进度概览或重复步骤状态。

| 状态 | 含义 |
| --- | --- |
| ❔ 待确认 | 关键需求或决定需要明确确认 |
| ⬜ 未执行 | 范围明确，尚未开始 |
| 🔄 执行中 | 实施、修复或验收失败后重开 |
| 🧪 待验证 | 实施完成，仍有适用验收未通过 |
| ✅ 执行完成 | 全部适用验收通过，证据完整；下一步和阻塞项均为无 |
| ⛔ 阻塞 | 写明原因及解除条件 |
| ⏸️ 已暂停 | 写明原因，下一步记录恢复条件 |
| 🚫 已取消 | 写明取消原因；保留原验收历史 |

验收行使用通过、失败、未验证、不适用；不适用必须写原因。普通明确需求直接执行，不为经过每个状态单独写记录或调用工具。重要决定、失败、修复复核、暂停及恢复只追加一次含时区的历史说明；历史不代表当前状态。

小需求仅需来源/范围、拆分理由、验收方式与依据、当前状态、下一步、阻塞项、AC 结果及必要历史。复杂需求的步骤表只列交付切片、依赖和 AC 编号，不复制验收结果或计数。独立子卡维护自己的 AC，父卡引用子卡证据，由负责人核对全部适用验收再完成；脚本不自动批准父项。

阶段结束及最终回复前，运行本需求 `delivery.py --requirement REQ-实际编号 finish`，命令自带写后核对，不再紧接着运行 --check；未提交也运行。脚本从卡片读取状态和验收，拒绝“完成但未验收”等矛盾，生成索引；相同事实重复收尾不写文件。多项收尾用 `finish --all`，只处理 1.7 新建的 v3 卡；不批量验收、不扫描旧 v2 完成卡。--check 仅供 CI 或独立只读核对。失败必须修正卡片或说明阻塞，不能交付相互矛盾的状态。向用户汇报直接采用卡片状态。

实际验收完成后，先在卡片更新 AC 证据与完成状态，再执行本需求 `finish --accept --inputs 本次源码目录 相关测试目录`，将实际验收范围和证据绑定。`--inputs` 为项目相对文件/目录，可删除项仍保留原路径；不填时首次采用全工作区，后续沿用原范围。只在真实完成验收/复核时使用 --accept，不为消除报错而重复接受。

普通 finish 只检查并同步，不能创建或覆盖基线；已完成但无基线、范围内源码变化或 AC 证据变化会拒绝收尾。先重开相关 AC、实际复核并更新证据，再显式 --accept；代码变化而证据未更新时，即使 --accept 也会拒绝。正常暂存、提交与交付归档不改变已验收内容，无需重验。范围选择仍需语义检查，脚本不证明验收真实性。

历史卡不批量建立新基线。明确续接旧 v2 卡时先核对其实际验收，使用 --accept 建立当前范围；旧 v1 需按当前模板整理本需求。单一状态源保持在需求卡，基线 JSON 仅是工具生成的证据绑定，不另填一套开发状态。

先写验收条件，再选择最小合理实现；按文件/框架加载对应规范。只增加验证行为所需的测试，运行相关构建、测试或 lint；没有工程、工具或凭据则明确未验证及影响。关键验收未验证保持待验证或阻塞，不以“代码已写”标完成。

字号测试默认不包含超大字号（辅助功能的更大字体档位）。仅当用户明确要求，或已确认需求/验收标准明确列入时，才执行该范围；普通字号与常规字号适配仍按本次改动验证。未要求的超大字号记录为“不适用：未明确要求，按默认测试范围跳过”，不作为完成或提交阻塞项，也不声称已通过。此约定只调整测试范围，不要求关闭 Dynamic Type 或移除已有适配。需求完成与 Git 提交、上线状态分别记录。

业务构建、测试和静态检查按 [项目验证入口](PROJECT-CHECKS.md) 配置和执行，需求卡记录本次 profile、结果及证据；不可用工作流工具测试代替 App 验证。

## 5. 提交与交付

本地 Hook 和 PR 范围检查按 [Git 检查说明](GIT-CHECKS.md) 显式配置，保留既有 Hook；CI 必须使用明确 base/head，不执行暂存区空检查。

提交前按 [审查规程](REVIEW.md) 审查暂存改动，匹配指纹复用；未准备提交的工作可先验证和记录，不必为了审查擅自提交。暂存只选择本次应提交文件，先核对用户已有暂存内容。

需求与提交/PR/发布按 [交付追踪](DELIVERY.md) 关联：提交使用 Requirement 尾注，本阶段和提交后执行 delivery.py finish，已授权的远端工作完成后加 --github；汇报未关联或尚未归档的记录，验收与远端状态分别登记。生成概览不替代团队验收，不将打标签视为已发布。

交付说明：完成行为、需求编号/状态、验证结果、未解决问题及是否提交。缺陷带位置、触发条件、影响和修复建议；不制造泛化风险清单。仅发布工作流包时加载 [发布规程](RELEASE.md)。

## 6. 目录与 Git

```text
项目根目录/                     ← Git 根目录、Codex 打开位置
├── AGENTS.md                   ← 自动发现入口
├── .agents/skills/ios-team-flow/SKILL.md
├── .github/workflows/          ← GitHub 必须在根目录发现
├── .agents/teamflow.json       ← 项目接入版本（接入脚本生成）
├── App/                        ← 新生成工程；现有项目可保留原名
├── requirements/               ← 项目 PRD、需求卡和确认记录
├── logs/reviews/               ← 可提交的脱敏审查证据
├── scripts/                    ← 工作流与项目辅助脚本
├── tests/                      ← 工作流工具测试
└── dist/                       ← 本地分发 zip；由 Release 附件上传
```

不要另建嵌套 Git 仓库。工作日志、需求和脚本可正常 git add/push；`.gitignore` 不忽略整个 logs 或 scripts。大体积 xcresult、构建输出、私钥、用户隐私不入库，保留脱敏摘要或受控 CI artifact 链接。复制文件到目录不等于上传 GitHub；push 与 Release 由明确授权执行。

## 7. 团队验收

按 [团队验收与问题复核](ACCEPTANCE.md) 判断适用性，保留真实确认与失败复核历史；适用团队验收尚未完成时保持待验证。

业务 App 发布按 [App 发布流程](APP-RELEASE.md) 记录归档、TestFlight、审核和商店状态。

重大流程变更按 [业务场景试运行](SCENARIOS.md) 验证消费项目链路；真实项目证据与工具夹具结果分开记录。

## 8. 最小执行路径与上下文预算

1. 开始只读本入口、相关需求和本次 Git 差异；同一会话已读且未变化的规范不重读。
2. 新建产品才读 PRD 模板，已有业务工程才读现状入口，涉及的语言/UI 才读对应规范；按相关章节读取，避免整套文档拼接。
3. 一次整理验收和必要影响范围，实施后运行最小相关检查。状态、证据只写需求卡，原始输出留日志，汇报只给结论和路径。
4. 先完成卡片/证据与 finish，再暂存和审查。测试证据提交前用 verify --staged；审查回执单向关联需求，不把当前审查指纹写回卡片。
5. 已验证且输入未变不重跑测试，同一有效指纹不重复语义审查。仅需归档记录时审查本次记录差异，不重新审已提交代码。
6. 安装/升级、Hook/CI、团队详细验收、App 发布、工作流分发和真实场景试运行文档仅在进入对应阶段时加载。无人要求发布就不加载发布链路。

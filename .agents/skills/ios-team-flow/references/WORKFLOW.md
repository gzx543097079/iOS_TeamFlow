# iOS 工作流

本文件是主流程、需求状态和授权原则的唯一规则来源。专题只补充操作细节。

## 请求与范围

问答、检查、分析和建议直接处理，不建卡。开发变更创建或续接唯一需求卡；明确只加入待办时使用 `--queued`。同一需求续接原卡。

```sh
python3 scripts/teamflow.py req create --title "标题"
```

记录目标范围和可观察 AC；排除范围、根因和重要决定有内容才写。只有影响结果且无法安全推断的选择才询问用户。功能模板用作分析清单，普通功能直接写需求卡；复杂功能才单独保存设计决定并由卡片引用。新 App 按启动阶段整理，发布资料按需加载。

## 实施与验收

明确范围 → 实施与随改随测 → 最终验收 → 按明确目标交付。

首次使用环境或环境变化时预检工具、依赖和目标。实施期间运行最小相关测试。收尾时确认代码、测试、文档和配置不再计划修改，再运行覆盖本次范围的验证；具体命令与证据绑定见 [PROJECT-CHECKS](PROJECT-CHECKS.md)。

适用检查通过且所有 AC 已确认才能完成；真机、视觉、账号或业务 AC 尚待实际确认时保留未完成项，进入待用户验证。用户确认后更新对应 AC，再完成需求。自动检查通过不自动代表人工 AC 通过。

```sh
python3 scripts/teamflow.py req complete REQ-0001 --profile change
# 人工 AC 尚待确认时，追加 --wait-user
```

已有验证结果时使用 `--result` 绑定；已绑定证据时可直接 `req complete REQ-0001` 复用并复核，不重跑测试。证据以 JSON 对象保存在卡片唯一的“验证证据”字段。没有自动检查但有可定位人工证据时使用 `--evidence`。相关验证输入变化后重新验证；状态、AC 完成图标和证据记录更新不使证据失效。

## 状态与记录

需求卡和需求列表使用固定图标；默认创建为 `🔵 进行中`。

| 状态 | 含义 |
| --- | --- |
| ⚪ 待处理 | 已记录，尚未开始 |
| 🟡 待确认 | 等待必要业务选择 |
| 🔵 进行中 | 分析、实施或验证 |
| 🟣 待用户验证 | 自动检查已完成，等待实际确认 |
| ✅ 完成 | 全部 AC 已确认且适用验证通过 |
| 🔴 阻塞 | 外部条件阻止继续 |
| 🟠 暂停 | 用户明确暂停 |
| ⚫ 取消 | 用户明确取消 |

AC 使用 `- ⚪ AC-01：条件` 或 `- ✅ AC-01：条件`，不叠加复选框。列表进度使用 `⚪ 0/N`、`🔵 M/N`、`✅ N/N`。需求状态、AC 和证据只维护一份，不额外手填验证状态。

通用 `req state` 可更新工作状态；完成和待用户验证统一通过 `req complete` 绑定证据。待确认、阻塞、暂停和取消须记录原因。只在重要决定、失败或返工时追加含时区记录，不填“无阻塞”等空项。

## 授权与停止

Git 和 App 外部动作必须由用户明确目标授权。自动补齐目标不可缺少的前置，执行到目标即停止；不扩张到可选配置、相邻动作或后续动作。前置需要无法推断的业务选择或超出当前范围时询问。

Git 目标按 [GIT-ACTIONS](GIT-ACTIONS.md)，App 目标按 [APP-RELEASE](APP-RELEASE.md)。准备或检查是只读的。需求完成本身不授权这些动作。没有外部目标时，完成验收即结束；独立新问题报告用户，不自动扩张范围。

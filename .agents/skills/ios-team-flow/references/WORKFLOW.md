# 单人 iOS 完整工作流

成员只有用户本人和 Codex。用户提出目标、回答必要业务问题、执行或授权外部动作；Codex 负责分析、实施、验证和维护唯一需求卡。没有团队角色、多人验收台账或派生交付总表。

## 1. 识别请求

| 请求类型 | 默认处理 |
| --- | --- |
| 问答、检查、分析、建议 | 直接处理；不建卡、不运行完成或交付动作 |
| App、代码、Bug、配置或产品行为变更 | 创建或续接一张 `REQ-0001` 格式需求卡 |
| 明确加入待办但暂不实施 | 建卡并标 `⚪ 待处理` |
| Git 或 App 外部动作 | 加载用户明确点名的目标动作专题；自动补齐不可缺少的前置，不串联可选或后续动作 |

## 2. 需求分析

在唯一需求卡记录范围、不包含内容和可观察 AC。普通明确需求直接进入实施；只有会改变结果且无法安全假设的决定才标 `🟡 待确认`。不为固定模板询问无关信息。

新 App 启动只填写启动模板。功能实施前只展开当前功能模板。发布资料只有用户明确提出发布准备或具体 App 外部动作时才加载。

## 3. 跟踪状态

需求卡和需求列表的状态只使用以下固定图标与中文语义；默认明确需求创建后即为 `🔵 进行中`。

| 状态 | 含义 |
| --- | --- |
| ⚪ 待处理 | 已记录，尚未开始 |
| 🟡 待确认 | 等待必要业务选择 |
| 🔵 进行中 | 正在分析、实施或验证 |
| 🟣 待用户验证 | 自动验证完成，等待用户实际确认 |
| ✅ 完成 | AC 与适用验证均已完成 |
| 🔴 阻塞 | 因外部条件无法继续 |
| 🟠 暂停 | 用户明确暂停 |
| ⚫ 取消 | 用户明确取消 |

AC 进度同样使用颜色语义：未完成项写为 `- [ ] ⚪ AC-xx`，完成项写为 `- [x] ✅ AC-xx`；列表汇总中 `⚪ 0/N` 表示尚未完成，`🔵 M/N` 表示部分完成，`✅ N/N` 表示全部完成。验证状态使用 `⚪ 未验证`、`🟣 待用户验证` 或 `✅ 通过`。

状态、范围、AC 和验证证据只在需求卡维护。没有内容时不生成拆分、下一步、阻塞或进度字段。只在重要决定、失败、返工、暂停或取消时追加含时区记录。

## 4. 实施与验证

按需求路由必要工程上下文、架构、语言和 UI 规范。默认顺序固定为：完成全部改动 → 环境预检 → 针对性测试 → 文件冻结 → 一次完整验证 → 目标交付。

“完成全部改动”包括本次代码、测试、文档、配置、版本和需求范围；不要在这些输入尚会继续调整时提前运行完整 profile。环境预检只核对工具、依赖、目标、模拟器/设备和必要账号是否可用，不代替测试。实施中使用最小相关测试快速反馈，失败修复后继续针对性测试。

准备收尾时先冻结验证输入，再按 [PROJECT-CHECKS](PROJECT-CHECKS.md) 执行一次匹配范围的完整验证；原始结果保存到 `logs/project-checks/<运行编号>/result.json`。完整验证后只更新不会进入指纹的状态与证据字段；如果代码、测试条件、文档、配置、版本或其他受跟踪输入变化，原证据失效，必须重新冻结并验证。测试不能证明的真机、账号、视觉或业务结果标为 `🟣 待用户验证`。

所有 AC 完成后执行：

```sh
python3 scripts/teamflow.py req complete REQ-0001 --result logs/project-checks/运行编号/result.json
```

没有自动检查但有可定位人工证据时使用 `--evidence`。需要用户实际确认时加 `--wait-user`。完成动作只更新需求卡，不创建 delivery JSON、审查回执或归档提交。

## 5. Git 动作

只有用户明确要求对应 Git 动作时才处理。commit 前暂存本次范围并运行 `python3 scripts/teamflow.py git check REQ-0001 --result ...`；它核对暂存对象与验证结果，但语义理解仍由 Codex完成。commit 写 `Requirement: REQ-0001` trailer。提交关联从 Git 动态查询。

用户没有提出 Git 目标时，不执行任何 Git 写操作。用户明确目标后，自动执行目标尚缺的最小必要前置：例如发布包含当前工作区改动的 GitHub Release，可依次完成验证、范围暂存、commit、push、标签和 Release；创建 PR 时可先推送目标分支。必要前置之外仍不扩张：commit 不自动 push，push 不自动开 PR，PR 不自动合并，Release 不代表 App Store 发布。

## 6. App 外部动作

只有用户明确指出目标动作时才读取 [APP-RELEASE](APP-RELEASE.md)。检查或准备是只读的；执行目标前自动补齐确实缺失的 Archive、上传等最小必要前置，但不自动执行目标之后的分发、审核或发布。前置需要版本、账号、测试组或发布方式等额外选择且无法从请求确定时，先停止询问。

TestFlight 上传还有一层独立边界：普通“上传 TestFlight”不得启用 `TestFlight Internal Only`。只有用户明确要求仅内部测试时，才写入 `testFlightInternalTestingOnly: true`；没有明确要求时完全省略该 ExportOptions 键。

## 7. 停止条件

需求达到 AC 且适用验证完成即结束主流程。未获明确目标指令时，不继续到 commit、push、PR、上传、审核或发布；已获目标指令时只走到该目标并包含必要前置。发现新问题只在影响当前 AC 时继续处理；独立问题报告给用户，不自动扩大范围。

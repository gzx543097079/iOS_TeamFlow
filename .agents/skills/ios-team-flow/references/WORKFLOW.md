# 中文 iOS 团队工作流

本文件只定义日常顺序和记录归属。成员提出需求、确认必要业务决定和验收、授权交付；Codex 负责建卡、实施、验证、同步与提交前审查。普通明确需求直接推进，无变化的问答不创建记录或执行收尾。版本见 [VERSION](VERSION)。

## 1. 接收与项目识别

先读 Git 状态、相关需求和现有项目入口，续接同一需求，不按对话轮次重复建卡。新需求由 Codex 执行 `delivery.py create --title "需求标题"`，生成按 UTC 时间排序的需求卡到项目根 requirements/。不补同步历史需求。

明确缺陷按 [Bug 修复与历史](BUGFIX.md) 使用专用模板；同一缺陷续接原卡，保留失败尝试及复核事实。

新产品先按 [启动模板](templates/new-project.md) 整理具体草案，团队明确确认启动范围后再建工程；确认功能和发布配置的时机由模板规定。默认建议不能视为批准，未回复不是确认。已有工程按 [现状流程](EXISTING-PROJECT.md) 增量处理，保留实际框架、语言、部署目标和目录；没有 .xcodeproj 也可能是生成式工程。工作流工具仓库不是新 iOS 产品。

新工程启动范围确认后，按 [Scene 生命周期](APP-LIFECYCLE.md) 生成 UIKit / SwiftUI 对应入口，并将成品配置、实际窗口和启动日志纳入验收；文件存在不等于 Scene 已生效。

新工程启动范围确认后，按 [日志组件](LOGGING.md) 自动复制对应语言源码、加入实际构建目标并配置 Debug/Release；使用安装工具返回的文件清单完成工程生成，不另行询问是否加入。

接入只在首次或明确升级时按 [INSTALL](INSTALL.md) 执行。空目录首次收尾前初始化 Git；已有仓库使用原根，不嵌套。

## 2. 一次确定范围与验收

在卡片写当前行为、预期行为、范围和可观察 AC。单一可验收结果在一张卡完成；多个独立结果、复杂交易/权限/数据变更或不同负责人时按交付结果拆分。步骤只引用 AC 和依赖，只有可独立交付或独立负责时另建子卡，父子双向引用，不复制状态。

普通明确且低风险改动可自审；商业规则、重要交互、新产品或高风险变更按 [ACCEPTANCE](ACCEPTANCE.md) 判断团队验收。在卡片一次记录验收方式和理由。缺项只阻塞依赖它的工作，独立工作继续推进。

## 3. 实施、验证与唯一记录

生成和修改业务代码时按 [中文注释](standards/comments.md) 说明职责、约束和关键原因。按实际改动读取 [OC](standards/objective-c.md)、[Swift](standards/swift.md)、[SwiftUI](standards/swiftui.md)；SwiftUI 同时读 Swift，所有 UI 改动读 [UI](standards/ui.md)，.mm 同时遵守工程 C++ 约定。已有团队明确约定优先，差异说明原因；不顺手迁移无关代码。

按 [PROJECT-CHECKS](PROJECT-CHECKS.md) 运行必要检查；缺陷尽量先复现，原有失败与新增问题分开。工具测试不代替 App 验证；关键检查缺工具或失败时保持未验证，不伪填通过。未明确要求不测试超大字号，其他明确验收仍执行。

| 信息 | 唯一维护位置 |
| --- | --- |
| 当前需求状态、AC 结果、下一步、阻塞及重要决定 | 需求卡 |
| 稳定工程入口、约定及资料来源 | PROJECT-CONTEXT（已有项目）或已确认 PRD（新产品） |
| 可执行验证命令与 profile 范围 | .agents/project-checks.json |
| 测试原始输出、对象指纹 | logs/project-checks 的实际结果；卡片引用 |
| 多人/多轮确认原始证据 | 按需验收历史；卡片引用，不复制当前结果 |
| 提交、PR、Release 事实及验收对象绑定 | delivery 工具生成；不手填 |
| 提交语义审查结论 | logs/reviews；单向引用需求和测试结果 |

状态可直接跳到实际阶段，无需为经过每一项单独写记录：

| 状态 | 条件 |
| --- | --- |
| ❔ 待确认 | 关键决定待明确确认 |
| ⬜ 未执行 | 范围明确，尚未实施 |
| 🔄 执行中 | 实施或失败后修复 |
| 🧪 待验证 | 实施完成，适用验收未完成 |
| ✅ 执行完成 | 适用 AC 均通过，有证据，下一步和阻塞项为无 |
| ⛔ 阻塞 | 写明原因和解除条件 |
| ⏸️ 已暂停 | 写明原因，下一步为恢复条件 |
| 🚫 已取消 | 写明原因，保留历史 |

AC 仅使用通过、失败、未验证、不适用；判定需有证据或理由。只追加重要决定、失败及复核的含时区记录，不复制完整输出或重复进度表。团队确认必须来自真实回复。

## 4. 验收与交付

状态、AC 或交付事实变化后，由 Codex 按 [DELIVERY](DELIVERY.md) 同步一次；事实未变不因回复或阶段名称再执行 finish。实际验收完成时显式绑定证据；自动测试优先引用 result，人工验收补充实际范围。已封存验收证明当时对象，不持续约束以后所有需求。明确续接或发现回归时重开相关 AC，新需求承担自己的验证。

待团队验收时也可按授权提交、推送或开 PR，需求保持待验证；不为交付代码强行标完成。合并/发布遵守已有验收规则。

有提交授权时按 [REVIEW](REVIEW.md) 暂存、审查并执行一次最终门禁；它同时核对引用测试与暂存内容。输入未变不重测、不重复语义审查。没有授权不 commit/push/release。

实施提交使用 Requirement 尾注；交付事实变化后同步记录。生成记录可以随下一次正常提交归档；需要本轮立即归档时仅审记录差异，不重审业务代码、不重新填写业务检查理由。归档不加实施尾注，避免循环登记自身 SHA。交付说明报告实际验收、验证限制、Git 状态和未归档记录。

Hook/PR 检查按需读 [GIT-CHECKS](GIT-CHECKS.md)；App 发布读 [APP-RELEASE](APP-RELEASE.md)，工作流 ZIP 发布读 [RELEASE](RELEASE.md)。GitHub Release 不代表 App Store 上线。重大流程变更按 [SCENARIOS](SCENARIOS.md) 验证消费链路。

## 5. 按需改进

出现已复现流程缺陷、重复返工或用户明确纠正时，按 [自我进化](EVOLUTION.md) 定位原因、控制范围并验证最小改进；当前任务中的必要修复及时处理，收尾只在有遗漏的改进事项时补记。复用需求卡与已有证据，无触发不写复盘、不自动开启下一轮任务。

## 阅读与目录边界

同会话已读且未变化的规则不重读；专题只在对应阶段读取，不拼接整套规范。读取先用路径、符号或差异定位，再展开必要上下文；不默认遍历全仓源码、requirements/ 或 logs/。跨会话从当前需求卡和工程现状续接，只在追溯问题时加载历史，不另建一套状态摘要。

工具保留既有逐项结果和状态快照输出；排错时按需展开相关原始日志。完整证据保存在文件，不复制到需求卡、审查报告和回复。外部构建/测试的长输出也保存日志，明确保留退出码；不能用截断输出代替失败判断。验证范围覆盖关联输入，不能为了复用证据排除共享代码、工程配置或依赖。

记录采用简短结论和可定位证据；问题展开触发条件、影响与处理。精简篇幅不减少 AC、七维语义审查、指纹和最终门禁。节省 token 的比例需实测，不作固定承诺。

规则只维护在 Skill 内，需求、工程、日志在项目根；不在 references 下创建业务产物。脱敏记录可提交，密钥、用户数据和大型构建产物不入库。既有工程保留目录，新工程默认 App/。

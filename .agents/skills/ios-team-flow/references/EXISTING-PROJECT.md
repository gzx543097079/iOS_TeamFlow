# 已有项目：首次摸底与增量开发

适用于已有业务工程中的功能迭代、缺陷修复和范围明确的重构。接入脚本只配置工作流入口；本流程由 Codex 在首次处理业务需求时执行。纯咨询不创建项目记录。

## 1. 识别项目及本次目标

先读 Git 状态、AGENTS.md 和已有项目说明，再结合 `.xcodeproj`、`.xcworkspace`、Package.swift、工程生成配置、源码和 CI 判断。没有 PRD 不代表新项目，没有 .xcodeproj 也不代表空项目；工程可能由工具生成。区分空目录、新产品、已有业务工程、仅有组件的包以及工作流/工具仓库。

多个 App、Target 或 Scheme 时先从需求、目录和项目记录确定本次目标；无法确定时只询问这个关键问题，可继续阅读共同配置。不要创建第二个 App 或嵌套 Git 仓库。已有仓库中新建独立产品时，对新产品使用新项目 PRD 流程，原工程保持原有配置。

## 2. 首次摸底与项目现状记录

优先复用已有的项目说明、架构记录与构建文档；按 [项目现状模板](templates/project-context.md) 创建或补充 `requirements/PROJECT-CONTEXT.md`，可通过链接引用现有材料，不另抄一套。多 App 在同一文档内按目标分节。

只记录稳定事实和配置来源；本次验收、测试结果和阻塞留在需求卡。先记录足以实施本次需求的信息：工程入口、目标 Target/Scheme、语言/UI 框架、架构和目录、部署目标、依赖、构建/测试配置入口、相关功能入口。主题、导航、权限、语言、订阅和打点按可得证据及本次关联范围记录。首次摸底不等于全仓审计，不为了填满模板阅读所有源码或运行全部测试。

按章节统一记录代码/配置/文档来源与最近核对时间，必要时记录提交 SHA；仅有来源不同或尚未核实的条目单独标注，不逐行重复时间和状态。代码推断不等于产品确认，未知项不能用新项目默认值补齐。没有完整材料时先记录已有事实，只对影响本次实现的缺项询问，不要求用户补一份完整新项目 PRD 才能开始。

后续需求先读现状记录，再核对相关配置是否变化。发生 Target、工具链、框架、依赖或业务约定变化时更新对应条目，保留变更记录；不每次重新摸底。现状记录是索引和证据，不高于用户要求或实际工程配置；矛盾时核实并纠正。

### 大型项目的模块路由

普通项目直接搜索入口、相关符号和调用者。仅在大型工程已启用索引或明确需要减少重复定位时，使用 [MODULE-CONTEXT](MODULE-CONTEXT.md) 的建立、检查和更新流程。

PROJECT-CONTEXT 只链接 `.agents/project-modules.json` 及已有架构资料，不复制模块表或动态结果。逐步记录实际触达模块，不预先扫描全仓。索引是可失效的定位辅助，实际工程和本次影响分析优先。

## 3. 沿用已有配置

已有项目不套用新项目默认值。默认沿用实际语言、UI 框架、架构、目录、最低系统、依赖管理、导航/Tab Bar、深色模式、语言范围、权限和签名配置。例如现有 SwiftUI、OC、Tab Bar 或禁用深色模式均保留，不因接入工作流改成 Swift + UIKit、iOS 14、无 Tab Bar 或开启深色模式。

新代码优先复用项目组件、样式、导航、服务和测试模式，同时按实际语言加载对应规范。项目现有明确约定优先；发现与通用规范不同，记录本次采用的方案及原因，不顺手迁移无关代码。需要调整架构、最低系统或其他基础配置时，将具体变化、影响和理由纳入需求范围确认。

## 4. 本次需求与影响分析

使用 [需求卡](templates/requirement.md) 记录用户期望、当前行为、修改后行为和验收条件，链接项目现状。小需求直接执行；复杂需求按工作流拆分。只跟踪本次增量，不重新描述整个产品。

按风险检查相关页面、组件、调用者、接口、存储、订阅、权限、多语言和打点；不记录无关项。涉及共享组件时检查受影响使用方。涉及存储迁移、认证或订阅权益时明确兼容性、已有用户路径与恢复/回退方案，不假设卸载重装即可解决。

## 5. 修改前基线与实施

按本次改动选择最小有用的基线：缺陷尽量先复现，工程或依赖修改先确认相关构建，纯文档不要求 App 构建。记录命令、Target/Scheme、设备/系统、结果和原有失败；命令来自实际项目，不猜测工具链版本。不擅自重置用户数据或清理已有改动。

已有失败与本次引入的问题分别记录。原有不相关失败不自动扩大整改范围；如果它阻止本次关键验收，说明限制并保持相关验收待验证/阻塞，不能将未验证写成通过。

实施限定于需求及必要关联改动，避免无关目录迁移、全仓格式化、依赖升级和机械重构。记录新增技术债或必须跟进的问题，不把所有历史问题塞入当前需求。

## 6. 回归与完成

验证本次功能和实际受影响路径，必要时执行相关单元/UI 测试、构建及人工验证。测试范围基于影响分析，不默认全仓全设备矩阵；无明确要求不测试超大字号，明确约定的验收仍执行。

沿用工作流的单一需求卡和验证证据，不另外手写进度概览。历史问题独立标记，不能把它们归因为本次改动。完成说明包含改了什么、相关验证和原有失败或限制；只有用户明确要求 Git 动作时才处理暂存、提交、推送、标签或 GitHub Release。项目配置改变时更新现状记录；脚本接入成功不代表业务构建或用户验证通过。

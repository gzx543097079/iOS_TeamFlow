# 团队验收与问题复核

实施前在需求卡确定适用验收、负责人及环境。普通文档/工具小改动可由自动检查和 Codex 自审验收；涉及产品行为、设计、商业规则或需求已约定团队验收时，必须留下团队实际确认。未知负责人写待确认，不能填写虚构姓名。

| 证据层 | 谁提供 | 证明范围 |
| --- | --- | --- |
| Codex 自审 | Codex | 本次差异的语义审查及限制 |
| 构建与测试 | 实际执行者/CI | 指定代码、配置、环境下执行过的检查 |
| 团队验收 | 产品、设计、测试或指定成员 | 明确版本上约定业务结果的接受 |

三者分别记录；review 通过、测试退出码 0、用户要求提交均不自动等于产品验收通过。使用 [验收记录模板](templates/acceptance.md)，存入 requirements/acceptance/REQ-编号.md。需求卡关联记录，交付工具的开发状态只汇总结果，不验证确认人的身份。

## 操作流程

1. 交付可审阅结果：需求与验收编号、commit SHA（未提交时用 review 指纹）、App 版本/build、设备/系统/语言/环境、测试证据、已知限制。
2. 团队需要验收时标 🧪 待验证，提交具体结果给负责人；记录原始确认文本或可访问工单链接、确认人及含时区时间。Codex 可以转录用户真实回复，不能自行署名代替确认。
3. 每条验收标通过、未通过、未验证或不适用及理由。全部适用验收通过才将需求标 ✅ 执行完成；非阻塞建议与阻塞缺陷区分。
4. 失败生成稳定问题编号（如 REQ-编号-B01），记录复现步骤、期望/实际、影响和证据，需求回到 🔄 执行中。无法继续时标 ⛔ 阻塞及解除条件。
5. 修复记录对应 SHA/指纹；执行原失败场景及关联回归，再由原验收角色复核其负责项目。保留原失败记录，不删行或改写成通过。
6. 代码、商品配置或环境变化影响已验收行为时，将相关项重开为待验证；沿用未受影响证据并写明理由，不重复整个验收，也不沿用已失效结论。

发布前仍有阻塞项不得标已验收；未验证项不能以“无发现”替代通过。没有明确要求不验证超大字号。

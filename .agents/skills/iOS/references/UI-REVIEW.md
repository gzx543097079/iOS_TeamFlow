# UI 评审与打磨

用户要求评审、走查或检查界面设计质量，上线前打磨，或需求含视觉 AC 时加载。只读评审不建卡；按评审结果修改时建卡或续接原卡，验收和授权按 [WORKFLOW](../../../teamflow-core/references/WORKFLOW.md)。实现规则见 [UI 规范](standards/ui.md)，本专题只补评审方法和打磨顺序。

## 范围与依据

- 先确定页面、流程和对应源码。依据优先级：需求卡与用户明确要求 > 工程现状的设计约定 > 同类页面的现有做法 > UI 规范。明确的需求胜过个人审美。
- 按页面类型调整要求：任务型（列表、设置、编辑、工具）以熟悉、清晰、一致为先，品牌只体现在强调色、字体细节、内容和动效；说服型（付费墙、引导）可以更有表现力，同时遵守[付费 UI](standards/ui-paywall.md)；阅读型（帮助、说明）先保证结构和可读性。
- 打磨保留，重做替换：打磨保持现有视觉、文案、行为和范围外内容；方向本身不对时说明理由并建议重做（另建卡），不借打磨偷换设计。改动事实性文案或新增宣称前先问用户。

## 取得证据

截图来自用当前代码重新构建并安装的模拟器或真机 App，旧构建的截图不算证据；不用浏览器或 Preview 代替。用测试数据或启动参数准备有内容的状态，空状态另截一张。模拟器未启动时先启动；多个模拟器运行时用 UDID 代替 `booted`：

```sh
xcrun simctl bootstatus <UDID> -b                   # 启动并等待就绪
xcrun simctl io booted screenshot <路径>.png
xcrun simctl ui booted appearance dark              # 结束后恢复原值
xcrun simctl ui booted content_size extra-extra-extra-large
```

- 覆盖本次涉及的设备类型（至少一台 iPhone，支持 iPad 时加一台 iPad）、浅色与深色、至少一种非开发语言或长文案；字号核对到常规最大档，辅助功能超大字号按 UI 规范只在明确要求时测试。
- 交互、焦点、VoiceOver 和恢复路径通过实际操作或 UI 测试确认，截图只证明画面。
- 写明证据来自模拟器还是真机；手势、触感、性能和传感器需要真机，未取得时标为未验证。
- 一次改完一批再统一截图核对，不改一处截一次；截图放临时目录或需求卡引用的位置，项目没有截图基准时不提交。

## 评审维度

每项按 0–4 评分：0 不可用，1 主要缺陷多，2 部分达标，3 良好仅有小问题，4 优秀。

| 维度 | 核对 |
| --- | --- |
| 平台一致性（关键） | 熟练的 iPhone 用户会信任它，还是会被不像系统的控件卡住：系统导航与模态、边缘返回、Safe Area、系统控件、SF Symbols；有无“网页移植感” |
| 层级与任务 | 主要操作和当前状态一眼可见；同一处可选项不超过 4 个；加载、空、失败、权限、禁用、成功状态齐全；文案说明动作和后果 |
| 无障碍 | VoiceOver 名称、特征、顺序；Dynamic Type 不截断不重叠；热区 44 pt；减少动态效果；两种外观的对比度 |
| 外观一致性 | 语义色与设计变量、单一强调色、字体层级、组内紧组间松的间距、同族图标、同一组件跨页一致 |
| 适配与性能 | 小屏、iPad 尺寸类、横竖屏、键盘遮挡、本地化长文案；启动、滚动掉帧、大图解码 |

合计 20 分：18–20 只需微调，14–17 补弱项，10–13 需要较多修改，9 分及以下建议重做相关部分。另用一句话判断设计针对性：换成无关产品是否也能原样使用。

## 问题分级

- **P0 阻断**：无法完成任务、数据丢失、误导性状态、无法访问的路径；立即修。
- **P1 主要**：明显困难，或违反审核要求、平台规范；发布前修。
- **P2 次要**：有绕过办法的困扰；下一轮修。
- **P3 细节**：几乎不影响用户；有空再修，少列，避免淹没重点。

每条写明位置（页面、`文件:行`）、维度、对用户的影响、依据（UI 规范条目或 HIG）和修改建议。只报实际核对过的问题。

## 报告

1. 结论：是否像原生 App，列出平台一致性违规；设计针对性一句话。
2. 评分表与合计。
3. 按 P0–P3 列问题；重复出现的模式单列为系统性问题（如“15 处硬编码颜色”）。
4. 做得好的 2–3 点，供后续沿用。
5. 建议：哪些问题合并进一张卡、按 P0 到 P1 的顺序修。评审不改代码，等用户决定。

## 打磨顺序

先读工程现状的设计约定、共享组件和相邻流程，再把每处偏差归类：缺少设计变量、一次性实现应改用共享组件、流程或层级与同类页面不一致（属于方向问题，先问）、局部缺陷。在最窄的正确层级修复。

按顺序处理，不在一个角落精修而其余部分仍低于同一标准：

1. 阻断任务、数据丢失、误导性状态、无法访问的路径；
2. 缺失的加载、空、失败、成功、禁用、权限状态；
3. 流程、层级、适配与设计系统偏差；
4. 视觉与动效不一致；
5. 代码与资源清理。

视觉 AC 按主流程由用户确认，用 `--user-confirmed` 记录。

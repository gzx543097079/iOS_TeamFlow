# PR、评审与 CI

用户明确提出创建 PR、评审、处理评审意见或接入 CI 时加载。授权与停止见 [WORKFLOW](WORKFLOW.md#授权与停止)，Git 动作范围见 [BOUNDARIES](BOUNDARIES.md#显式-git-动作)。

## 创建 PR

一张需求卡对应一个 PR；同一 PR 含多张卡时，每张卡都须完成或明确标为阶段提交。描述直接由卡片生成，不另写一份范围或验证结论：

```sh
python3 scripts/teamflow.py req pr REQ-20260101-a3f9
```

输出首行为标题，其余为正文（范围、不包含、AC 进度、证据摘要、未确认 AC 与 `Requirement:` 尾注）。只补充评审者需要的上下文，如截图链接、迁移步骤或已知风险；未验证项保持“未验证”，不改写成通过。创建 PR 不包含合并、开启自动合并、指定评审人或打标签，除非用户明确要求。

## 评审

评审他人 PR 默认只读分析并在对话中给出结论；发布评论、批准或请求修改属于外部动作，需用户明确目标。按以下顺序核对，只报告有证据的问题：

1. 改动是否落在卡片“范围”内，有无“不包含”中的内容或无关文件。
2. 每条已勾选 AC 是否有对应的自动证据或可定位的人工证据；人工、视觉与真机条件是否仍标为未验证。
3. 证据是否对应提交内容：`git ci` 或 `req status` 显示有效或交付时有效。
4. 凭据、个人数据、生成产物和本地日志是否误入提交；依赖变化是否按[依赖与工具链](DEPENDENCIES.md)处理。
5. 数据迁移、公共接口和共享配置变化是否写入 AC 并有回归。

## 处理评审意见

范围内的修改续接原卡：改代码后重跑必要检查，AC 文字变化即视为需求语义变化，证据失效并重新验收。超出范围的建议另建卡或记录为后续，不在本 PR 扩张。每轮修改后重新 `git check` 再提交。检查只复核证据；提 PR 或合并不会自动触发全量测试。基线合并、冲突解决或依赖变化影响验证输入时，再运行覆盖影响面的 profile。

## CI 核对（可选）

[CI 模板](../assets/ci/github-teamflow.yml)在 PR 中运行只读核对，确认本 PR 改动的完成卡，其证据对应当前内容或某个交付提交：

```sh
python3 scripts/teamflow.py git ci --base origin/main
```

它不重跑项目检查，只证明“提交的内容就是验证过的内容”；进行中的卡只提示，不阻塞。需要 CI 重新执行检查时，在模板中按项目平台启用 `verify run` 任务（iOS 需要 macOS runner，Godot 需要安装锁定版本的引擎）。CI 需要完整历史（`fetch-depth: 0`）。接入 CI 本身是用户明确目标，模板复制到 `.github/workflows/` 后由团队提交。

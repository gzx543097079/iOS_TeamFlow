# 工作流

本文件是主流程、需求状态和授权原则的唯一规则来源。专题只补充操作细节；命令参数见 [COMMANDS](COMMANDS.md)，检查触发与证据见 [CHECKS](CHECKS.md)，Git 范围见 [BOUNDARIES](BOUNDARIES.md)。

## 按需读取

首次只读 AGENTS 所选模式的 Skill 入口和本文件。Skill 名称与引用表只是目录，按任务选用。

- 按本次操作和实际语言读直接相关专题；进入后续阶段再补读。
- 跨平台只引用实际涉及的语言、桥接或平台专题，不读另一 Skill 完整入口。
- 同会话已读且未变的内容直接复用；变更、缺失或新专题时只补必要内容，不建加载台账。
- 新会话续接进行中需求时，先 `req status <编号>`，只读剩余工作需要的专题。
- 项目事实从已有资料或 `PROJECT-CONTEXT.md` 定位相关条目；稳定结论改变时就地更新；无入口时按[项目现状模板](templates/project-context.md)补充，不另建记忆文件。
- 改 Skill、安装或工具时，只核对本次要改的入口与引用；修工作流时读 [REPAIR](REPAIR.md)。

## 请求与范围

问答、检查、分析和建议直接处理，不建卡。开发变更创建或续接唯一需求卡；只加入待办时用 `--queued`。

轻量改动不建卡：同时满足不改变运行行为（文案措辞、注释、文档、格式或拼写），且不涉及依赖、工程配置、权限、支付、数据和公共接口。直接修改并做最小核对；提交不带 `Requirement:` 尾注；钩子对仅含 `.md`/`.rst` 的暂存放行。实施中发现不满足条件时立即建卡。

```sh
python3 scripts/teamflow.py req create --title "标题"
```

记录目标范围和可观察 AC；排除范围、根因和重要决定有内容才写。只在选择影响结果且无法安全推断时询问。功能模板作分析清单。已有工程新增模块、改跨模块接口、数据迁移，或有影响结果的多种方案时，实施前把方案要点写入「决策与异常」，经用户确认再实施；方案较长时另存设计文件由卡片引用。新 App 首版按启动模板记常规默认，只有关键取舍无法推断时询问；发布资料按需加载。

## 实施与验收

明确范围 → 集中实施与按需检查 → 最终验收 → 按明确目标交付。

非工程产物按 [ARTIFACTS](ARTIFACTS.md) 分类存放。首次或环境变化时预检工具与依赖。同一需求内局部低风险改动集中实施，结束后统一快速检查：一张卡、一次验收、一次提交（分任务阶段提交除外，见下表）。

实施中只为定位缺陷、验证关键行为或消除具体风险而检查；失败只重跑失败项；长验证后台运行并等宿主完成通知，不用固定时长 sleep。日常用 `verify run --profile <名> --requirement <编号>`；定稿用 `req complete --profile` 绑定证据（自动复用本需求有效完整结果）。提交/PR/合并不升级为全量；Release 仅显式 `manual` profile。细节见 [CHECKS](CHECKS.md)。

### 改动分级

按影响判定，不按行数。展示与行为同卡时按最严；可拆 AC，不得把行为写成「小 UI」降测。轻量不建卡见上节。

| 级别 | 条件（须全部满足才算小改动） | 验收 |
| --- | --- | --- |
| 小改动 | 仅单页/单组件展示（布局、间距、对齐、字号颜色、工程内换图、语义不变文案）；不改请求/登录会话/共享状态/数据匹配/权限支付关键写入/跨模块契约；不改测试所断言的产品行为 | 适用触发检查通过后默认 `--wait-user`；最多两轮；不为纯视觉自跑全量单测或全量 UI 测 |
| 须扩大检查 | 任一：登录/会话；请求或筛选；媒体/加载策略；数据匹配或契约；共享状态影响他页；跨模块接口；权限/支付/关键流程；工程配置或依赖 | 适用自动检查 + 受影响范围定向测（模块 check 或 `-only-testing`）；无对应 check 则定向测或交接表标未验证；用户确认不替代自动证据 |

### 完成与人工确认

适用检查通过，且每条 AC 已按证据确认。小改动与视觉类 AC 默认用户验收；明确确认即人工证据。

| 模式 | 触发 | Agent 做法 | 提交 / 正式 PR |
| --- | --- | --- | --- |
| 完整交付（默认） | 未声明分任务 | 自动检查 → 勾选表 + `--wait-user` → 用户确认后 `--user-confirmed` | 确认（或 `--waive-human`）之后 |
| 分任务交付 | 用户明确「每个任务单独提交推送」等 | 子任务保持进行中；中途不 `--wait-user`；整批结束再总表 | 阶段 commit/push 可用进行中+自动证据；正式 PR 仍须确认 |

长任务：先做完可独立工作，最后一张表（检查项、通过/失败/未验证、依据、待勾选），再 `--wait-user`。用户明确免除时才 `--confirm-ac` 并加 `--waive-human`；沉默不等于免除。命令见 [COMMANDS](COMMANDS.md)；门禁见 [BOUNDARIES](BOUNDARIES.md)。

阻塞和取消须按用户明确决定恢复后再验收。证据摘要写入卡片头部。

## 状态与记录

`req create` 生成含头部与正文的卡。工具读写头部；正文只勾选 AC、向「决策与异常」追加；`〈…〉` 不能验收。

| 状态 | 含义 |
| --- | --- |
| 🔵 进行中 | 分析、实施或验证；`queued: true` 表示排队 |
| 🟣 待用户验证 | 自动检查完成，等待确认 |
| 🔴 阻塞 | `blocked`：待确认 / 外部 / 暂停 |
| ✅ 完成 | 全部 AC 已确认且适用验证通过 |
| ⚫ 取消 | 用户明确取消 |

AC 为 `- [ ] AC-01：条件`。确认绑定范围、不包含与该条文字；文字变则旧确认失效。状态与证据只维护一份。`req state` 更新工作状态；完成与待用户验证统一经 `req complete`。阻塞/取消/恢复/重开须记原因；重开用 `--reopen-ac`。

## 并行与子 Agent

- 交派写明编号、范围与需读专题；接手先 `req status`。
- 一张进行中卡同一时间只由一个会话推进；并行用独立分支或 worktree。
- 连续加派：并入本卡、`--queued` 或另卡；分任务提交时勿双会话抢同一卡。
- 子 Agent 只做分析或局部实施；验收与 Git 由主会话执行。

## 授权与停止

同一目标已明确授权时不重复征询；宿主工具审批仍须遵守。Git 与 App 外部动作只按用户明确目标执行：补齐必需前置，到达即停。前置需无法推断的业务选择或超出范围时先问。需求完成本身不授权 Git/发布；无外部目标时验收完成即结束。

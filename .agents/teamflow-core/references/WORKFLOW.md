# 工作流

本文件是主流程、需求状态和授权原则的唯一规则来源。专题只补充操作细节。

## 按需读取

首次只读 AGENTS 所选模式的 Skill 入口和本文件。Skill 的名称、描述和引用表只是目录，按任务选用。

- 按本次操作和实际语言读取直接相关的专题；进入后续阶段时再读对应资料。
- 跨平台任务只引用实际涉及的语言、桥接或平台专题，不读另一 Skill 的完整入口。
- 同一会话已读且未变化的内容直接复用；文件变更、上下文缺失或进入新专题时只补读必要内容，不建加载台账。
- 新会话续接进行中的需求时，先运行 `req status <编号>` 取得状态、剩余 AC 和下一步，只读取剩余工作需要的专题。
- 项目事实从已有资料或 `PROJECT-CONTEXT.md` 定位，只读本次相关条目与来源，不遍历历史卡。稳定结论改变时就地更新原资料及来源；无合适入口时按[项目现状模板](templates/project-context.md)补充，不另建记忆文件。
- 修改 Skill、安装或工作流工具时，读取本次实际要改的入口和引用以核对关联。
- 修复缺陷或改进工作流时读 [REPAIR](REPAIR.md)。

## 请求与范围

问答、检查、分析和建议直接处理，不建卡。开发变更创建或续接唯一需求卡；只加入待办时用 `--queued`。

轻量改动不建卡：同时满足不改变运行行为（文案措辞、注释、文档、格式或拼写），且不涉及依赖、工程配置、权限、支付、数据和公共接口。直接修改，按实际情况运行覆盖改动的最小检查或人工核对，向用户报告结果；用户要求提交时，提交消息不带 `Requirement:` 尾注；提交钩子对仅含 `.md`/`.rst` 的暂存直接放行。实施中发现不满足条件时立即建卡。

```sh
python3 scripts/teamflow.py req create --title "标题"
```

记录目标范围和可观察 AC；排除范围、根因和重要决定有内容才写。只在选择影响结果且无法安全推断时询问用户。功能模板作分析清单。已有工程中新增模块、改变跨模块接口、数据迁移，或存在影响结果的多种可行方案时，实施前把方案要点（改动位置、接口、取舍）写入卡片“决策与异常”，经用户确认再实施；方案较长时另存设计文件由卡片引用。新 App 首版按启动模板把常规默认值记为决定，只有关键取舍无法推断时询问。新 App 按启动阶段整理，发布资料按需加载。

## 实施与验收

明确范围 → 集中实施与按需检查 → 最终验收 → 按明确目标交付。

实施中产生的非工程文件（设计稿、UI 预览、报告等）按 [ARTIFACTS](ARTIFACTS.md) 分类存入项目内目录，随写随建。

首次使用或环境变化时预检工具、依赖和目标。按改动范围和风险选择验证强度：同一需求内局部低风险的小改动集中实施，结束后统一跑一次覆盖本次范围的快速检查，一张卡、一次验收、一次提交。

实施中只为定位缺陷、验证关键行为或消除具体风险运行检查；调试失败只运行失败的用例或检查，不在 TeamFlow 外重复跑全套测试。耗时较长的验证放后台运行并等待宿主的完成通知，不用固定时长 sleep 轮询。代码、测试、文档和配置定稿后，通过 `req complete --profile` 统一验收并绑定证据，不先直接跑完整命令再为绑定补跑；若已用 `verify run --requirement`，通过 `--result` 绑定。证据仍有效时直接复用，验证失败或相关输入变化后重跑必要检查；提交、提 PR 或合并本身不升级为全量验证。按 check 范围触发适用检查，未覆盖工程改动阻断；未触发不冒充通过。Release 构建仅显式发布 profile 执行，不混入日常验证。检查选择、结果输出和证据绑定见 [CHECKS](CHECKS.md)。

完成条件：适用检查通过，且每条 AC 已按实际证据确认。自动检查不代表人工 AC 通过，也不自动勾选；未确认的 AC 保持进行中；真机、视觉、账号或业务 AC 由用户确认：用 `--wait-user` 进入待用户验证，用户在对话中明确确认后用 `--user-confirmed AC-编号` 勾选并完成，不用 `--confirm-ac` 自行勾选。

```sh
python3 scripts/teamflow.py req complete REQ-20260101-a3f9 --profile change
# 按实际证据确认 AC 并复用证据完成
python3 scripts/teamflow.py req complete REQ-20260101-a3f9 --confirm-ac AC-01
```

阻塞和取消须按用户明确决定恢复后再验收。

完成时证据摘要写入卡片头部，绑定与失效规则见 [CHECKS](CHECKS.md#证据)。命令报错或参数不明时再读[命令参考](COMMANDS.md)，常规完成只需上方两条命令。

## 状态与记录

需求卡由 `req create` 生成，含头部元数据和 Markdown 正文（范围、不包含、验收条件、决策与异常）。工具读写头部（编号、类型、状态、阻塞原因、证据摘要），在正文中只勾选或取消 AC、向“决策与异常”追加状态记录；其余正文可自由编辑；`〈…〉` 是占位，不能验收。

| 状态 | 含义 |
| --- | --- |
| 🔵 进行中 | 分析、实施或验证；`queued: true` 表示排队未开始 |
| 🟣 待用户验证 | 自动检查已完成，等待实际确认 |
| 🔴 阻塞 | 停止推进；`blocked` 记录类型：待确认（等待业务选择）、外部（外部条件）、暂停（用户明确暂停） |
| ✅ 完成 | 全部 AC 已确认且适用验证通过 |
| ⚫ 取消 | 用户明确取消 |

AC 使用 GitHub 任务列表 `- [ ] AC-01：条件`。需求状态、AC 和证据只维护一份，不额外手填验证状态。

`req state` 更新工作状态；完成和待用户验证统一通过 `req complete` 绑定证据。阻塞须用 `--blocked` 指定类型并以 `--reason` 记录原因；取消须记录原因；从阻塞或取消恢复为进行中须按用户明确决定并记录依据；重开已完成的需求用 `--reopen-ac` 取消需重新验收的 AC 并记录原因。只在重要决定、失败或返工时追加含时区记录，不填“无阻塞”等空项。

## 并行与子 Agent

- 子 Agent 和新会话不继承当前上下文：交派时写明需求编号、本次范围与需读的专题；接手方先运行 `req status <编号>`。
- 一张进行中的卡同一时间只由一个会话推进，其他会话只读或另建卡；并行修改使用独立分支或 worktree。
- 子 Agent 只做分析或局部实施；验收、`req complete` 和 Git 动作由主会话执行。

## 授权与停止

同一目标已明确授权时不重复征询；宿主另行要求的工具审批仍须遵守。Git 和 App 外部动作只按用户明确的目标执行：自动补齐目标必需的前置，到达目标即停，可选配置、相邻或后续动作不做。前置需要无法推断的业务选择或超出当前范围时先询问。

Git 目标按 [BOUNDARIES](BOUNDARIES.md#显式-git-动作)，App 或游戏外部目标按当前模式 Skill 路由的发布专题；准备和检查是只读的。需求完成本身不授权这些动作，没有外部目标时验收完成即结束；独立的新问题报告用户，不扩张范围。

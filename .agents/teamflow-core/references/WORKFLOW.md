# 工作流

本文件是主流程、需求状态和授权原则的唯一规则来源。专题只补充操作细节。

## 请求与范围

问答、检查、分析和建议直接处理，不建卡。开发变更创建或续接唯一需求卡；明确只加入待办时使用 `--queued`（进行中但排队）。同一需求续接原卡。

```sh
python3 scripts/teamflow.py req create --title "标题"
```

记录目标范围和可观察 AC；排除范围、根因和重要决定有内容才写。只有影响结果且无法安全推断的选择才询问用户。功能模板用作分析清单，普通功能直接写需求卡；复杂功能才单独保存设计决定并由卡片引用。新 App 按启动阶段整理，发布资料按需加载。

## 实施与验收

明确范围 → 集中实施与按需检查 → 最终验收 → 按明确目标交付。

首次使用环境或环境变化时预检工具、依赖和目标。根据改动范围和风险选择验证强度。同一需求内、影响局部且风险低的小改动可集中实施，结束后统一运行一次覆盖本次范围的快速检查；不按文件或修改点重复建卡、执行完整流程或提交。

实施期间仅在定位缺陷、验证关键行为或消除具体风险时运行相关检查。收尾前确认代码、测试、文档和配置不再计划修改，再统一验收；已有检查覆盖本次范围且证据仍有效时直接复用。验证失败或验证后相关输入发生变化时，重新运行必要检查。检查选择、简短结果输出和证据绑定见 [CHECKS](CHECKS.md)。

适用检查通过且所有 AC 已确认才能完成；真机、视觉、账号或业务 AC 尚待实际确认时保留未完成项，进入待用户验证。用户确认后更新对应 AC，再完成需求。自动检查通过不自动代表人工 AC 通过。

```sh
python3 scripts/teamflow.py req complete REQ-20260101-a3f9 --profile change
# 人工 AC 尚待确认时，追加 --wait-user
```

验证通过后，根据实际证据确认指定 AC，再复用证据完成：

```sh
python3 scripts/teamflow.py req complete REQ-20260101-a3f9 --confirm-ac AC-01
```

自动检查不自动勾选 AC。未确认条件保留进行中，明确等待用户实际确认时才使用 `--wait-user`；全部 AC 确认后直接完成。占位范围或 AC 不能验收，阻塞和取消须先按用户明确决定恢复。

完成时把证据摘要（profile、结果、输入指纹、需求指纹、HEAD、时间）写入卡片头部；本地日志不提交，删除后仍可按摘要复核。人工证据同时绑定需求语义与核对文件快照，变化后必须重新实际验证。状态、AC 勾选和证据记录不使绑定失效。命令参数、人工范围与复用规则见 [命令参考](CHECKS.md#命令参考)。

## 状态与记录

需求卡由头部元数据和 Markdown 正文组成。工具只读写头部（编号、类型、状态、阻塞原因、证据摘要）；正文的标题、排版和“决策与异常”可自由编辑。编号形如 `REQ-20260101-a3f9`（日期 + 随机后缀），多分支并行创建不冲突。

```markdown
---
id: REQ-20260101-a3f9
type: feature
state: 进行中
created: 2026-01-01T10:00:00+08:00
---

# 登录失败提示优化

## 范围

登录接口返回错误时，在表单下方展示可读提示。

## 不包含

无

## 验收条件

- [ ] AC-01：密码错误时显示“账号或密码错误”

## 决策与异常
```

证据只绑定“范围”“不包含”和各 AC 文字；勾选、标题、排版与记录变化不影响证据。`〈…〉` 是占位，不能验收。

| 状态 | 含义 |
| --- | --- |
| 🔵 进行中 | 分析、实施或验证；`queued: true` 表示排队未开始 |
| 🟣 待用户验证 | 自动检查已完成，等待实际确认 |
| 🔴 阻塞 | 停止推进；`blocked` 记录类型：待确认（等待业务选择）、外部（外部条件）、暂停（用户明确暂停） |
| ✅ 完成 | 全部 AC 已确认且适用验证通过 |
| ⚫ 取消 | 用户明确取消 |

AC 使用 GitHub 任务列表 `- [ ] AC-01：条件` / `- [x] AC-01：条件`。列表进度使用 `⚪ 0/N`、`🔵 M/N`、`✅ N/N`。需求状态、AC 和证据只维护一份，不额外手填验证状态。

`req state` 更新工作状态；完成和待用户验证统一通过 `req complete` 绑定证据。阻塞须用 `--blocked` 指定类型并以 `--reason` 记录原因；取消须记录原因；从阻塞或取消恢复为进行中须按用户明确决定并记录依据。只在重要决定、失败或返工时追加含时区记录，不填“无阻塞”等空项。

## 授权与停止

Git 和 App 外部动作必须由用户明确目标授权。自动补齐目标不可缺少的前置，执行到目标即停止；不扩张到可选配置、相邻动作或后续动作。前置需要无法推断的业务选择或超出当前范围时询问。

Git 目标按 [BOUNDARIES](BOUNDARIES.md#显式-git-动作)，App 目标按 [APP-RELEASE](../../skills/iOS/references/APP-RELEASE.md)。准备或检查是只读的。需求完成本身不授权这些动作。没有外部目标时，完成验收即结束；独立新问题报告用户，不自动扩张范围。

## Bug 修复

新缺陷创建：

```sh
python3 scripts/teamflow.py req create --bug --title "缺陷标题"
```

复现、根因和失败尝试有事实时补充到原卡，省略空字段。优先记录可复现条件、期望、实际和影响，再定位根因。能安全复现时先保留失败证据；修复后重跑原失败场景及受影响回归。环境或历史失败与本次新增问题分开。

同一缺陷复发时续接原卡并重开受影响 AC；独立根因另建卡。只有实际发生的重要失败、尝试、修复和复核写入“决策与异常”，不另建台账。

## 按证据改进工作流

只在已复现流程缺陷、重复返工、重复无效操作或用户明确纠正工作方式时使用。未经验证的猜测、单次网络波动和个人偏好不固化为通用规则。

1. 在当前需求卡写明触发、范围和可观察 AC。
2. 定位最小根因，优先修正旧规则或工具，不叠加第二套台账。
3. 保留修复前失败与修复后通过的同一场景；纯措辞调整不增加无行为价值的测试。
4. 使用可比较的命令次数、文件数量、耗时或实际 token 数据说明效率变化；没有可靠数据不承诺比例。
5. 改进失败或成本高于收益时停止并撤销本次可归因改动。

流程改进授权不包含 commit、push、发布或任何 App 外部动作。删除兼容代码或旧入口必须由本次范围明确允许。

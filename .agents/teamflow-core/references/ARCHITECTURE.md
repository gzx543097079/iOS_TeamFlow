# 按需求架构生成与审查

适用于生成业务代码、功能扩展及明确的架构重构。需求文档已确认的架构、模块边界和依赖方案是实施约束，不能用个人偏好或模板默认建议替换。已有需求记录和本次用户明确更正可作为依据；无冲突不再次索要确认。

## 实施前定位归属与已有能力

先定位需求或工程现状中的既有架构决定，再搜索本次相关功能、组件、工具及真实调用方。普通功能沿用现有职责和接口，无需逐需求重写映射。只有新增或改变模块边界、依赖方向、状态所有权时，在原需求卡或工程现状补充受影响的职责、位置和接口；其他记录链接引用。

资料缺失时先从相关代码核实。常规实现选择由实际工程和本次目标决定；只有无法安全推断的关键架构取舍或决定冲突才询问，独立工作继续。已有模块索引按 [MODULE-CONTEXT](MODULE-CONTEXT.md) 辅助定位，不把索引未变化当作架构正确的证据，也不默认全仓扫描。

## 模块边界与依赖

- 按业务职责及状态所有权划分模块，例如账号、商品、购物袋和订单；不机械地每页一个模块。模块只公开真实使用方需要的入口、数据和协议，其他实现保持最小访问范围。
- 跨模块通过明确的公开接口协作，不直接访问对方节点／控制器内部、私有模型或存储。应用或游戏组装层负责依赖和跨模块导航；功能通过回调或明确契约表达导航意图。
- 依赖必须无环，共享层不反向引用具体业务功能。外部服务优先构造注入，状态来源与生命周期明确，避免服务定位器和隐式全局可变状态。不为单个场景制造空协议、万能基类或无用途的 Repository/UseCase。
- 共享 UI 通过数据和回调接入，不读取某页面的私有状态。具有业务含义的规则保留在相应业务模块或明确的领域服务，不因多处调用就塞进通用工具层。

### 保持现有工程结构

默认在现有工程内划分逻辑职责，不因目录增多自动拆分编译单元、Package 或仓库。改变实际工程结构需属于本次明确范围，并核对生成配置和资源引用。

## 复用判断

复用看业务语义、状态所有权和变化原因是否一致，不只看相似代码或重复行数。

| 实际情况 | 处理方式 |
| --- | --- |
| 已有能力满足需求 | 直接复用 |
| 职责一致，仅缺少少量能力 | 扩展原实现，检查已有调用方 |
| 多处实现语义与变化原因一致 | 抽取共同能力并迁移实际使用方 |
| 代码相似，但业务规则或状态生命周期不同 | 保持独立，不用大量开关强行统一 |
| 只有一个实际场景，尚无独立边界需求 | 优先保留在所属模块，不提前加入公共层 |

共用层只放实际共用的能力，保持接口内聚；避免将页面细节抽成泛型参数、配置开关或继承层级转移复杂度。单个使用方也可因外部依赖隔离或真实独立边界需要抽取，但须能说明用途，不以未来可能复用为依据。

## 工具类按职责收敛

| 能力 | 归属 |
| --- | --- |
| 无状态计算、格式转换 | 对应职责的函数或小类型 |
| 网络、存储、图片加载 | 基础设施服务 |
| 会话、权限及订单等业务规则 | 所属业务模块或明确的领域服务 |
| 通用按钮、空状态与样式 | 公共 UI 层 |
| 页面专用辅助逻辑 | 页面或所属功能模块内部 |

不向 `Utils`、`CommonManager`、`BaseTool` 等万能容器继续堆叠职责；Swift extension、Objective-C category 也不能成为无关业务的入口。已有大工具类只按本次涉及职责逐步拆分，先搜索同义能力，避免改名后产生第二套实现。

接口明确输入输出、失败行为、线程/隔离要求及副作用。无状态工具不隐藏读取当前用户、当前页面、网络或全局存储；有外部依赖的能力通过参数或构造注入，作为明确服务管理。缓存、订阅、长任务和共享可变对象明确所有者、隔离和释放策略，不用新增单例掩盖归属问题。

## 抽取与迁移闭环

1. 定位重复实现和真实调用方，核对行为差异、边界条件及资源引用。
2. 确定唯一职责与接口，保留需求确认的行为，再迁移本次范围内使用方。
3. 删除已无引用的旧实现、空包装、无用配置和资源；不能只新增公共实现却让旧副本继续承担同一规则。检查代码外的 工程配置、场景／界面配置、运行时类名或注册表引用，不能只凭文本搜索无结果删除。
4. 验证共同能力与受影响调用方；确需分批迁移时，在原需求卡写清剩余范围与原因，不重复维护迁移台账，不宣称已全量收敛。

明确授权清理的内部实现可直接替换，不无故保留兼容包装。已发布公共接口、持久化数据和外部协议仍按实际契约判断；数据变化遵循 [ARCHITECTURE](#数据迁移与恢复)，不能把“删除旧工具”扩张为破坏用户数据。

## 生成后核对

按本次实际影响面将适用结果写入原需求 AC，证据只引用一份。提交时复用未变结论，仅复查新增差异：

1. 实际类型职责、状态所有权和依赖符合已确认架构；控制器不残留应属于 View数据／服务的业务处理。
2. 模块只暴露必要接口，依赖无环，公共层不反向引用业务页面；保持既有工程结构，文件或资源移动后实际成员关系与加载正确。
3. 共用能力有真实调用方，核心业务规则有唯一权威实现；不同业务语义未被强行合并，工具接口无隐式全局依赖。
4. 本次范围内调用方迁移完成，已删除实现无残留引用，既有行为和失败语义没有非预期改变。
5. 对核心输入输出与边界做独立单元验证，按影响检查取消、并发、缓存隔离、订阅和对象释放，并回归原 UI 主路径；编译通过不能证明架构或复用正确。

未取得的行为或运行证据如实保留未验证。本次范围之外的既有架构问题记录边界，不无条件重构全项目；不新增全仓扫描、审批或重复清单等强制前置。

## 数据迁移与恢复

仅在持久化模型、文件格式、数据库结构或跨版本数据契约变化时加载。沿用项目既有迁移机制，不为普通功能新增迁移框架。

1. 核对实际旧版本、数据规模和存储位置；在需求 AC 中明确已有用户的升级结果，不能以卸载重装证明迁移成功。
2. 使用脱敏样本或项目内合成数据复现旧格式，验证正常迁移、空数据、中途失败、重复执行与恢复；记录不可逆步骤。
3. 定义迁移前后版本判断、写入原子性及幂等行为。备份只在明确位置与范围内创建，涉及项目外真实数据先取得本次明确授权。
4. 核对旧版读取新版数据的兼容性；若不支持降级，明确限制，不能承诺代码回退等于数据恢复。
5. 失败时保留可定位证据，按既定恢复方案处理；不得自行清空用户数据或扩大到生产环境。

决定与结果写入原需求卡或引用项目既有迁移说明，不新建固定审批表。

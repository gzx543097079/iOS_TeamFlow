# 升级时识别旧形态验证配置并在升级中迁移

## 范围

用户指出升级到 1.5.0 后 Slipwise 的 change profile 仍是单个全量检查（check_app.py 内含 Release 模拟器构建，与 cloud-release 的 release-build 重复），且无 check covers 导致每次整组执行，要求在版本升级时处理掉。升级工具不猜测改写项目脚本：doctor 新增「验证配置形态」，日常（非 manual）profile 的命令或其引用的项目脚本含 Release 构建列为需处理并指出与其他 profile 的重复，未声明 check covers 列为提示；upgrade 完成后用新核心复核并报告“验证配置待迁移”。INSTALL 规定出现该项时在同一次升级任务中另建卡迁移项目脚本与配置，CHECKS 增加从全量脚本迁移的步骤。随本卡定版发布 TeamFlow 1.6.0。

## 不包含

升级工具自动改写项目脚本或 project-checks.json；修改 Slipwise、颜见；verify migrate 配置草稿；多卡共用一次验证。

## 验收条件

- [x] AC-01：doctor 对日常 profile 的命令或引用脚本含 Release 构建报「验证配置形态」需处理并指出重复的 profile，manual profile 不报；未声明 check covers 只报提示，不改变退出码；有修复前失败的回归测试
- [x] AC-02：upgrade 完成后以新核心复核验证配置，旧形态时输出“验证配置待迁移”与迁移指引，并在 --json 结果中给出；无配置或已迁移时不输出
- [x] AC-03：INSTALL 写明待迁移时在同一次升级任务中另建卡迁移、用户暂缓须记录原因；CHECKS 增加从全量脚本迁移步骤；TRIAL 与 CHANGELOG「未发布」记录依据，validate_workflow 与全量测试通过
- [x] AC-04：版本升为 1.6.0，workflow-release 测试与打包通过，PR 以 Merge 合并，GitHub Release 公开且四个 ZIP 与 SHA256 齐全

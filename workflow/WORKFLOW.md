# 中文 iOS 团队工作流

版本见 `workflow/VERSION`。先读 [UI 规范](standards/ui.md)，涉及其他类型再按入口加载。Codex 原生约定仅指根目录 AGENTS.md 与 `.agents/skills/<name>/SKILL.md` 的发现机制；本文流程是团队约定，不宣称存在官方统一 iOS 工作流认证。

## 1. 接收与需求追踪

先查看 git status、现有工程/文档/构建命令和相关需求，不覆盖已有工作。口头需求足以触发追踪：从 `templates/requirement.md` 创建 `requirements/REQ-YYYYMMDD-NNN.md`，同一天按未占用编号递增；创建使用排他写入或检查冲突。后续同一需求更新原记录，不能每轮对话建一张。

用户只问解释且不要求改动时无需建卡。用户明确取消要记录取消与原因；暂停记录暂停与恢复条件。持续推进已授权工作，只有新项目需求确认、关键缺失业务信息或实际需要授权的外部动作才等待；可独立完成的内容继续做。

## 2. 拆分判断（由 Codex 决定并记录理由）

小需求：单一可验收结果、影响集中、依赖已知、没有迁移或高风险交易/权限状态变更。在一张需求卡中直接执行，保留过程和验证即可。文件数/代码行数不是单独决定因素。

任一情形建议拆分：多个独立用户结果；跨 UI、服务、存储等边界且可分别验证；订阅权益、数据迁移、认证或复杂并发；未知技术方案需要先验证；存在外部依赖/多人协同；难以在一次清晰审查中解释完整变更。

拆分顺序：识别用户结果 → 标依赖和风险 → 按可演示的纵向能力切片 → 高风险先做最小验证 → 每步给验收条件与回退。通常 2–7 步只是参考，不凑步骤、不按文件机械拆分。父卡列子步骤；只有步骤可独立交付或有独立负责人时才另建子卡并双向链接。范围变化可重新拆分，保留原因与原历史。

示例：“改按钮文字”为小卡；“新增订阅中心”为产品配置与模型校验、套餐展示、购买恢复与权益、埋点和端到端验证等依赖步骤。改一行价格也可能涉及交易风险，需要专项核查，但不一定拆成多个卡片。

## 3. 新项目需求确认

新建 iOS 产品时先请团队提供已有 PRD、设计、接口及商业规则。即便材料不完整，也先用 `templates/new-project.md` 将用户已给内容整理成 `requirements/PRD-项目名-v1.md`，未知项标“待确认”，不要捏造套餐、价格或目标用户。

按模板逐项填写项目名称、Bundle ID（用户称 buildid 时同时确认含义）、版本/构建号、UI 框架、架构、主要开发语言、设备/工具链、环境与能力、多语言清单等工程配置。默认建议写入草案但标待确认，不能自动视为团队批准；保留模板的默认语言候选，按目标市场和翻译预算确认取舍。创建工程后补齐实际配置与构建命令，并验证它们和已确认 PRD 一致。

新项目默认使用 Swift + UIKit，最低支持 iOS 14.0；依赖与 API 选择需兼容该目标，不自动改用 SwiftUI 或提高最低系统版本。模板头部的文档版本、状态、产品负责人、技术负责人和更新日期逐项竖排。

创建工程前按模板第 3 节给出实际目录树、各层职责、依赖方向、Target/资源/配置归属及模块化决定。Apple 的文件/Group/Package 机制与团队 MVVM 目录约定分别说明。按确认功能创建必要文件，不空建所有示意目录；创建后验证工程引用、资源打包、构建和相关测试，不能把目录结构完成当作工程已可运行。

首版系统权限按模板独立列清单：从首版功能推导启用项，确认访问范围、系统用途文案、App 内提示、各语言翻译、请求时机和拒绝后处理。生成工程时落实到实际 Target 的配置、能力、文案资源和运行时请求代码，并验证实际授权路径。不得默认添加全部候选权限，不得把工程配置视为用户授权；缺资料或未验证项明确记录。

向团队呈现可审阅文档、范围及关键缺项，请其确认具体版本。记录确认人（未知就写团队用户）、时间、原始确认内容与版本；没有明确回复保持“待确认”，不得把等待时长当批准。确认前可调研、整理 UI 与技术建议；确认后再生成 `App/` 工程及业务代码。需求范围发生重大变化时形成新版本并确认变化部分。

## 4. 实施与状态机

`待确认 → 待开始 → 进行中 → 待验证 → 已完成`。普通明确小需求可直接待开始；任意未完成状态可进入“阻塞 / 暂停 / 已取消”。问题复现或验收失败从待验证/已完成返回进行中，并保留重开记录。

每次阶段变化、重要决定、验证失败、修复、阻塞和恢复追加带时区时间的过程记录。子步骤用 `未开始 / 进行中 / 已完成 / 阻塞 / 不适用`；完成需填写证据，不适用需写原因。父项全部适用验收达成才完成，不用完成百分比代替证据。

先写验收条件，再选择最小合理实现；按文件/框架加载对应规范。只增加验证行为所需的测试，运行相关构建、测试或 lint；没有工程、工具或凭据则明确未验证及影响。关键验收未验证保持待验证或阻塞，不以“代码已写”标完成。需求完成与 Git 提交、上线状态分别记录。

## 5. 提交与交付

提交前按 [审查规程](REVIEW.md) 审查暂存改动，匹配指纹复用；未准备提交的工作可先验证和记录，不必为了审查擅自提交。暂存只选择本次应提交文件，先核对用户已有暂存内容。

交付说明：完成行为、需求编号/状态、验证结果、未解决问题及是否提交。缺陷带位置、触发条件、影响和修复建议；不制造泛化风险清单。发布工作流执行 [发布规程](RELEASE.md)。

## 6. 目录与 Git

```text
项目根目录/                     ← Git 根目录、Codex 打开位置
├── AGENTS.md                   ← 自动发现入口
├── .agents/skills/ios-team-flow/SKILL.md
├── .github/workflows/          ← GitHub 必须在根目录发现
├── workflow/                   ← 工作流规则、UI/三类代码规范、模板
├── App/                        ← 新生成工程；现有项目可保留原名
├── requirements/               ← 项目 PRD、需求卡和确认记录
├── logs/reviews/               ← 可提交的脱敏审查证据
├── scripts/                    ← 工作流与项目辅助脚本
├── tests/                      ← 工作流工具测试
└── dist/                       ← 本地分发 zip；由 Release 附件上传
```

不要另建嵌套 Git 仓库。工作日志、需求和脚本可正常 git add/push；`.gitignore` 不忽略整个 logs 或 scripts。大体积 xcresult、构建输出、私钥、用户隐私不入库，保留脱敏摘要或受控 CI artifact 链接。复制文件到目录不等于上传 GitHub；push 与 Release 由明确授权执行。
